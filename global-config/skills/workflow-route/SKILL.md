# Secure workflow route

Load this skill via the native `skill({name:"workflow-route"})` tool at the start of every new user task. On a long-chat resume or after context compaction load it again before dispatch; re-read the current canonical `/home/james/ai-workspace/workflow_optimisation/WORKFLOW.md` when it changed, scope changed, or the prior route is uncertain. This user-owned recipe is the route authority. No skill grants tools or mutation permissions.

1. Check the secure project-registration gate before inspecting an unregistered root; use only the reviewed `host_register_project` control-plane operation when justified. For a read-only question without a project root, do not register a project.
   For project inspection, prefer available authorized `aft_outline`/`aft_zoom`, indexed `codegraph_codegraph_explore`, and structural `ast_grep_search`; read a known allowed file with a dedicated read tool. The approval-bearing built-in `grep` is reserved for this orchestrator. A child uses prompt-free `sandbox_grep` only for a bounded exact literal, configuration, or prose query that the semantic/structural tools cannot answer. Never bypass protected-path rules or substitute shell search.
2. Classify intent. Explanation, audit, comparison, diagnosis, planning and review remain read-only unless a change is explicitly authorized. If change intent is genuinely ambiguous, clarify before writer dispatch; do not invent authorization.
3. Classify authorized work by decision content using the recipe's Task Classes: tiny fix, small feature, substantial feature, bug investigation, documentation, or global tooling change. Decision content selects the route; file count, changed lines and risk never select it.
4. State `ROUTE: <class> | intent: <read-only/authorized change> | route: <skill/phase> | specialist: <name> | basis: WORKFLOW.md`. Load `workflow-odd-secure` for an ODD change; load `workflow-systematic` when the route invokes Systematic. Read and dispatch each installed upstream skill actually selected. For read-only answers load only what the specific question requires; do not launch a writer or create an ODD tracker.
   Carry the following compact contract into every mapping, implementation, and review Task brief that permits repository inspection: `SEARCH CONTRACT: AFT=navigation; CodeGraph=relationships/impact; AST-grep=structure; sandbox_grep=bounded literal fallback; native grep unavailable; no shell-search bypass.` If the child needs evidence outside its registered project, require it to stop and return exactly `EXTERNAL_CONTEXT_REQUIRED` plus `Purpose`, `Expected location`, and `Required evidence`. Resolve that separately through an approved exact-path read, a researcher registered for the other repository, or a dedicated host-config researcher when registered; never widen the child's host access.
5. Record the loaded skill and observed named Task dispatch, not just an intended route. If a required skill, Task tool, or safe execution surface is missing, report the affected work blocked; a read-only explanation may continue with limitations.

On resumption, repeat classification against the user's latest authorized scope. Read the existing `odd/tasks/<feature-name>.md` and its Magic Context mirror only for substantial ODD work. Do not store transient route state as a global memory. A compact session handoff should record project, authorized intent, task class, selected skill, named specialist, completed evidence and next step. Keep per-project coding-model and Sol-to-Astra decisions scoped to their original session/project; if unavailable after compaction, ask only when a pending eligible delegation needs the choice.

For a global config/plugin/skill change, implement in reviewed in-repo source, use the appropriate separate native review checkpoint when enabled, and deploy through the verifier mirror. Never edit host plugins/config as an orchestrator.

On a review-eligible project route, read native RDD mode status and carry its effective value and deciding source into the route record; v3.5 default-on is a valid source, and an explicit off is a valid user choice. Do not enable or disable RDD to satisfy verification.

Read [session decisions and registration](references/session-decisions.md) when coding model selection, an Astra recommendation, secure project registration, or a managed lifecycle handoff is relevant. These are user-owned compatibility decisions; do not infer them from upstream skills.
