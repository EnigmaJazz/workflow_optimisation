# OpenCode V2 operations runbook

This is the operating guide for the **live** OpenCode V2 install: how a change to documents, config,
skills, prompts, plugins, or a plugin version pin reaches the running server, and where that differs
from V1. It assumes the cutover is done. The one-time cutover, the install checklist, the manual
gates and the database swap are **not** repeated here; they are in
[`opencode-v2-cutover.md`](opencode-v2-cutover.md) and, for the stack itself,
`~/agent-sandbox-integration/docs/upgrades/opencode-v2.md`.

Validated against source revision: workflow repo, branch `docs/v2-docs-refresh`, HEAD `98c249d`
(2026-11-01). Re-check that revision before executing; if it has moved, re-validate every command
whose source changed (see [References](#references)). Anything this guide could not confirm from
source is marked **UNVERIFIED**.

Deployment is owner-run. Nothing in this repository applies a change to the live V2 install by
itself, and a `git commit` deploys nothing.

## Mental model

There are three places, and only one of them is edited.

| Place | Path | Role |
|---|---|---|
| Canonical source | `global-config/` in this repo | The only thing a writer edits. Reviewed in git. |
| Derived root | `~/.local/share/opencode-v2/config/opencode` | Generated by `scripts/derive-v2-config.py`. The server reads this. Never edit by hand. |
| Live process | `secure-opencode-v2.service` (port 4097) | Reads the derived root once, at start. |

```
global-config/  --derive --apply-->  ~/.local/share/opencode-v2/config/opencode  --start-->  secure-opencode-v2.service
     ^                                                                                              |
     |  tests, review, commit                                                                 restart only re-reads it
```

Four consequences follow, and they are the whole runbook:

1. **Editing the derived root is always wrong.** The next `derive` overwrites it, and the verifier
   reports the file as drift in the meantime.
2. **`derive` is not a side effect of anything else.** There is no automatic mirror step on V2. The
   V1 model ("verifier mirrors `global-config/` into `~/.config/opencode`, then restart") does not
   apply: V2's verifier is read-only and reports drift instead of repairing it
   (`verify/checkers/v2-config-check.py:6-7`: "V2's config root is generated and owned by the
   owner's `derive --apply`, so drift is reported, never repaired by the verifier").
3. **A restart alone applies nothing.** Restarting re-reads the same derived root; if `derive --apply`
   did not run, the bytes are the previous ones.
4. **Drift is the normal state after a verifier commit.** Any change under `verify/` or to
   `verify-workflow.sh` makes the derived health-check plugin stale until the digest is re-pinned
   and `derive --apply` runs (see [Plugin updates](#plugin-updates)).

`derive` mirrors a fixed set: `cli.json`, `AGENTS.md`, `systematic.jsonc`,
`rate-limit-fallback.json`, and the `prompts/`, `skills/`, `plugins/`, `mcp/` directories
(`scripts/derive-v2-config.py:34-35`). It also writes the Systematic overlay to
`<derived root>/../home/.config/opencode/systematic.jsonc`, because Systematic reads `$HOME/.config`
whatever `XDG_CONFIG_HOME` says (`scripts/derive-v2-config.py:426-436`).

Older text in this repository describes the V1 deployment model and still stands for V1:
`CLAUDE.md` ("Source → review → mirror", and "Deployment is not complete at commit"),
`WORKFLOW.md` ("Changes that deploy outside a git repo", "Health-check plugin lifecycle") and
`docs/TODO.md` Q53 ("a restart alone applies nothing … verifier mirror → restart"). Every one of
those statements is correct for V1 and wrong for V2, where the repair step is `derive --apply`
instead of the verifier mirror. Where they disagree with this runbook, this runbook governs V2.

What `derive` rewrites rather than copies is recorded in its docstring
(`scripts/derive-v2-config.py:7-17`): `plugin` becomes `plugins`; exact registry pins become
`~x.y.z` patch ranges; the rate-limit fork becomes a directory entry pointing at a copy under
`<root>/vendor/`; the auto-update and `opencode-usage-total` packages are dropped; `tui.json` is not
carried (V2 reads `cli.json`); V2's dead config keys are dropped; permissions are not rewritten but
**every sandbox tool needs an explicit rule**, and a tool registered in the sandbox repo without one
makes `derive` refuse (`scripts/derive-v2-config.py:100-106`).

The full derive command, used everywhere below:

```fish
python3 scripts/derive-v2-config.py --source global-config --sandbox-repo ~/agent-sandbox-integration --target ~/.local/share/opencode-v2/config/opencode
```

Add `--apply` to write. Without it, `derive` prints one `[derive-v2] would replace <path>` line (or
`would write` for a file that does not exist yet) per differing file, `note:` lines for meaning
changes, `WARNING:` lines, and ends with `dry-run - nothing was written`
(`scripts/derive-v2-config.py:409-423`). It refuses a target inside the V1 trees (`~/.config/opencode`,
`~/.opencode`) with exit 2, and keeps a `.bak-<timestamp>` next to every file it replaces. It never
deletes anything.

## Artifact classes

Pick the row, run the sequence, restart only when the row says so.

| Artifact | Canonical location | Apply | Restart | Verify |
|---|---|---|---|---|
| Skills, prompts, `AGENTS.md`, `systematic.jsonc`, `rate-limit-fallback.json` | `global-config/skills/`, `global-config/prompts/`, `global-config/*.json`, `global-config/AGENTS.md` | tests → commit → review → `derive --apply` | yes (server loads config at start) | `verify-workflow.sh`; preflight "config in sync" |
| `opencode.json` (agents, permissions, providers, MCP wiring) | `global-config/opencode.json` | same | yes | same; plus a `derive` dry run must print no `would` lines |
| `cli.json` (V2 CLI config) | `global-config/cli.json` | same | yes | preflight "config in sync" |
| Local MCP server code | `global-config/mcp/<name>/` | same; `derive` rewrites the server command into the derived root and adds V2-owned env (`scripts/derive-v2-config.py:151-171`) | yes | preflight; the MCP tools answer |
| Plugin source | `global-config/plugins/*.ts` | tests → commit → review → `derive --apply` | yes (plugin JavaScript loads at start) | preflight "tool registration" is PASS |
| Plugin version pin | `global-config/opencode.json` (`plugin` array) and `global-config/tui.json` | [`plugin_pins.py`](#plugin-updates) → `derive --apply` | yes | preflight "config in sync" |
| Verifier modules or `verify-workflow.sh` | `verify/`, `verify-workflow.sh` | [`verifier_manifest.py update`](#digest-pin-after-verifier-edits) → review → commit → `derive --apply` | yes | `verifier_manifest.py check`; preflight |
| systemd unit or GitHub drop-in | `changesets/opencode-v2-units/` | `changeset.py apply` → `systemctl --user daemon-reload` | yes, if the unit changed | preflight "unit files" is PASS |
| AFT backport | installed plugin cache (outside git) | [`patch-aft-v2-schema.py`](#the-aft-constraint) | yes | `--check`; preflight "tool registration" |
| Guarded plugin auto-update timer | `docs/systemd/v2-plugin-autoupdate.{service,timer}.template` | owner installs and enables; no repo script installs it | timer owns its restarts | `systemctl --user list-timers`; the JSONL log |
| Sandbox-repo S17 paths (`nono/profile/**`, `scripts/**`, `opencode/plugins/**` in `~/agent-sandbox-integration`) | that repository | owner only; proposals go in `docs/proposals-*.patch` | owner's call | owner |

Two rows are cross-repo and easy to get wrong:

- A **new sandbox tool** (a new `defineTool` in `~/agent-sandbox-integration/opencode/plugins/lib/tool-specs-*.ts`)
  needs an explicit permission rule in `global-config/opencode.json` in the same change set, or
  `derive` refuses with "tools without an explicit permission rule (V2 would allow them silently)"
  (`scripts/derive-v2-config.py:85-106`). V2 silently allows a tool that has no rule.
- A **new plugin entry** that is neither an exact registry pin, the rate-limit fork, nor a known drop
  makes `derive` refuse with "plugin entry needs a decision"
  (`scripts/derive-v2-config.py:74-77`). Decide deliberately: pin exactly, and `derive` converts it
  to `~x.y.z` for V2.

## End-to-end procedure

The order is forced. Each step says who runs it (see [Who runs what](#who-runs-what)).

1. **Edit in the repo.** A sandbox writer changes `global-config/` (or `verify/`, or the changeset
   set). The orchestrator stays read-only: it may read, route and review, never write or execute.
2. **Tests.** `python3 -m unittest discover -s tests` from the repo root. The V2 surface has its own
   suites (`tests/test_derive_v2_config.py`, `tests/test_v2_config.py`,
   `tests/test_verifier_v2_config.py`, `tests/test_verifier_v2_mode.py`,
   `tests/test_opencode_v2_preflight.py`, `tests/test_opencode_v2_units_changeset.py`,
   `tests/test_v2_plugin_autoupdate.py`, `tests/test_patch_aft_v2_schema.py`). A failing suite is a
   stop, not a warning.
3. **Commit.** Conventional commit, no attribution trailers. The commit is the review candidate; it
   deploys nothing.
4. **Native review, when due.** Review runs against the in-repo source candidate and produces
   evidence, not delivery authority. An unreviewed commit may be committed and installed but must be
   reviewed before it is treated as the boundary for later work.
5. **`derive` dry run (read-only, anyone).** Run the command from [Mental model](#mental-model).
   Read every `would replace` line: those are the files that will change. Read every `note:` line that
   starts with `moved` or `kept` — something changed meaning, not just bytes. A `refused:` exit 2
   means the source cannot be derived; fix the source, never the derived root.
6. **`derive --apply` (owner).** Same command plus `--apply`. Each replaced file gets a
   `.bak-<timestamp>` beside it. If the output reads `refused:`, nothing was written.
7. **Restart (owner).** `systemctl --user restart secure-opencode-v2.service`. Restart
   `opencode-perm-v2.service` too only when that unit or its script changed.
8. **Verify (read-only, anyone).** Run the verifier with the V2 binary resolving first on `PATH`:
   it derives the major version from `opencode --version` (`verify/21-opencode-major.sh:5-26`). If
   that detection returns 0 (no `opencode` on `PATH`, or an unparseable version), set
   `WORKFLOW_VERIFY_OPENCODE_MAJOR=2` explicitly — an undetected V2 behaves as V1 and tries to
   repair the V1 tree.

   ```fish
   bash verify-workflow.sh < /dev/null
   python3 scripts/opencode-v2-preflight.py --stack
   ```

   In V2 mode the verifier does not repair anything: section 0 replaces V1's recovery with a
   read-only derive dry run and fails with `V2_CONFIG_ROOT_DRIFT` when the root differs from
   `global-config/` (`verify/50-section-0-recover.sh:5-19`). `V2_CONFIG_ROOT_DRIFT` therefore means
   "run `derive --apply`", not "the verifier is broken". The preflight reports the same condition as
   a WARN ("run derive --apply") and fails only on version pin, service, registration or stack
   problems (`scripts/opencode-v2-preflight.py:68-108`); exit code 1 means at least one FAIL.
9. **Behavioral probes, when required.** Paid, so not on every change: demand one run after anything
   that changes probing or routing, and one before treating a verifier run as an acceptance gate.
   The key is read from the systemd manager; never paste it into a file or a terminal that logs:

   ```fish
   env POOL_PROXY_KEY=(systemctl --user show-environment | grep '^POOL_PROXY_KEY=' | string replace 'POOL_PROXY_KEY=' '') bash verify-workflow.sh --behavioral
   ```

10. **Record the deploy.** One row in `ROUTER-LOG.md` with the commit and the deploy target
    (`~/.local/share/opencode-v2/config/opencode`) as evidence.

**Stop rule:** if step 6 wrote files and step 8 still fails, do not re-run `derive --apply` hoping
for a different result and do not edit the derived root. Read the drift detail, fix the source, and
either commit a new change or roll the derive back ([Rollback](#rollback)).

## Plugin updates

### Version pins (human-approved)

`scripts/plugin_pins.py` consumes the auto-update plugin's proposals and edits the **canonical**
source only — `global-config/opencode.json` and `global-config/tui.json`
(`scripts/plugin_pins.py:1-11`, `:20`). It refuses to overwrite a pin that no longer matches the
proposal's base (`stale`), a name listed twice, a non-plain version, and a verdict other than
`propose` (`scripts/plugin_pins.py:79-108`).

```fish
python3 scripts/plugin_pins.py report
python3 scripts/plugin_pins.py apply --approve <name>=<version> --dry-run
python3 scripts/plugin_pins.py apply --approve <name>=<version>
```

Then the normal sequence: tests → native review → commit → `derive` dry run → `derive --apply`
(owner) → restart → verify. The `report` column "source differs from proposal base" is the `stale`
condition you will hit first; it means something else moved the pin.

A pin edit still has to survive `derive`'s plugin policy: exact pins become `~x.y.z` on V2, so V2
follows a patch release inside that range only through the guarded job below; a `~` or `^` in the
**source** is not a legal entry for `derive` at all (it expects an exact pin or a known drop).

### Guarded auto-update (V2 only)

`scripts/v2-plugin-autoupdate.py` is the V2 replacement for the retired auto-update plugin (which
`derive` drops). Only `~x.y.z` patch ranges are eligible; exact pins, `^`, `*`, `latest` and
non-registry specs are reported as ineligible and left alone (`scripts/v2-plugin-autoupdate.py:46-51`).

After `plugin update` it restarts the server, then **gates**: every plugin loaded before must load
again, and a failed plugin shows as ID `-`. On a failed gate it pins each updated package back to its
previous exact version with a timestamped config backup, restarts, and gates again
(`scripts/v2-plugin-autoupdate.py:141-163`). Exit codes: 0 nothing to do or updated and gated,
4 rolled back, 3 rollback failed the gate, 5 another run is active, 2 refused. Every step appends to
`<state-dir>/autoupdate.jsonl`.

The timer template runs daily at 04:30 with `Persistent=true` (`docs/systemd/v2-plugin-autoupdate.timer.template`);
the service template passes `--config ~/.local/share/opencode-v2/config/opencode/opencode.json`,
`--server http://127.0.0.1:4097`, `--state-dir ~/.local/state/opencode-v2-autoupdate`,
`--password-file ~/.local/share/opencode-v2/server-password` and
`--restart-cmd "systemctl --user restart secure-opencode-v2.service"`. The files are templates: the
owner installs them into `~/.config/systemd/user/` and enables the timer. Dry run before trusting it:

```fish
python3 scripts/v2-plugin-autoupdate.py --opencode ~/.local/share/opencode-v2/prefix/node_modules/.bin/opencode2 --server http://127.0.0.1:4097 --config ~/.local/share/opencode-v2/config/opencode/opencode.json --state-dir ~/.local/state/opencode-v2-autoupdate --password-file ~/.local/share/opencode-v2/server-password --dry-run
```

Two consequences worth a line each:

- A successful update touches only the package cache, so `derive` stays clean. A **rollback** writes
  an exact pin into the derived root's `opencode.json`, which is drift from `global-config/`
  (still `~x.y.z`). Re-run `derive --apply` to restore the shared pin, or approve the exact pin in
  the source through `plugin_pins.py`.
- A plugin-cache reinstall — including one this job performs — can discard the AFT backport. See
  [The AFT constraint](#the-aft-constraint).

### Digest pin after verifier edits

`verify-workflow.sh` embeds a sha256 manifest of every file under `verify/`, and
`global-config/plugins/workflow-health-check.ts` pins the entry's sha256; the plugin refuses a
mismatched script (`scripts/verifier_manifest.py:1-9`). After **any** edit to the entry or a module:

```fish
python3 scripts/verifier_manifest.py update
python3 scripts/verifier_manifest.py check
```

Then review and commit the changed plugin source, `derive --apply` (owner), and restart. On V1 the
verifier re-mirrored the plugin during its next run; **on V2 it does not**, so a `verifier_manifest.py update`
that is not followed by `derive --apply` leaves the derived plugin pinning an older script and the
preflight/config check reporting drift.

On V2 the health check does not start the verifier on its own: the plugin's V2 entry only launches it
when `WORKFLOW_HEALTH_CHECK_V2=1` is set (`global-config/plugins/workflow-health-check.ts:281-285`).
The digest pin still matters — it is what refuses a mismatched script once a check does run — but a V2
session does not show the V1 FAILED banner by default. Whether the live V2 launcher exports
`WORKFLOW_HEALTH_CHECK_V2` is **UNVERIFIED** (the launcher lives in the sandbox repo).

### The AFT constraint

AFT is the one plugin with a rule of its own, because no available version works unmodified:

- The source pins `@cortexkit/aft-opencode@0.62.0` exactly, in `global-config/opencode.json:3026`
  and `global-config/tui.json:8`.
- `V2_PLUGIN_VERSIONS` in `scripts/derive-v2-config.py:56` is **empty**, so V2 runs the same pin as
  V1 and there is no V2-only override. The comment above it (`:50-56`) still says "with it empty V2
  stays on OpenCode 2.2.0"; that sentence predates the 2.2.5 move and is stale. The empty map is the
  operative fact.
- OpenCode 2.2.1+ rejects every AFT 0.62.0 tool ("undefined is not an object (evaluating 'a.ref')",
  cortexkit/aft#1141). The fix (#1144) is plugin JavaScript only, so V2 keeps 0.62.0 and gets it
  applied to the installed copy (`scripts/patch-aft-v2-schema.py:1-15`).
- AFT 0.63.4 carries the fix but cannot start inside the V2 nono sandbox (its storage lease opens
  `/`; `docs/upstream/aft-storage-lease-root-open.md`). **Do not add it to `V2_PLUGIN_VERSIONS`**
  until upstream fixes the lease.

The patch runs against the installed package directory, never the config:

```fish
python3 scripts/patch-aft-v2-schema.py <plugin-dir> --check
python3 scripts/patch-aft-v2-schema.py <plugin-dir> --apply
```

`<plugin-dir>` is
`~/.local/share/opencode-v2/cache/opencode/npm/@cortexkit/aft-opencode@<pin>/<newest epoch>/node_modules/@cortexkit/aft-opencode`.
`--check` exits 0 only when every target is already patched; the patch refuses any other version or
build, is idempotent, and keeps `*.orig-0.62.0` (`scripts/patch-aft-v2-schema.py:104-133`). Run it
after any plugin-cache reinstall and before the restart. Restart after patching: the plugin bytes are
read at start. The preflight's "tool registration" check catches an unpatched plugin: the 2.2.5 trial
measured 20 to 40 `Skipping invalid` lines with it unpatched and 0 patched (see the cutover runbook).

## Who runs what

| Actor | May | Must not |
|---|---|---|
| Orchestrator | read, route, review, dispatch | edit or execute; run `derive --apply`; restart or call `systemctl` |
| Sandbox writer | edit the repo, run tests in the sandbox | touch the derived root; restart; commit |
| Owner | `derive --apply`, `changeset.py apply`, `systemctl --user`, S17 installs, secrets | — |

User-facing commands assume the owner's shell is Fish: no heredocs, no `$(...)` outside `bash -c`,
and `env VAR=(cmd) ...` for an environment variable from a command. Never print, store or echo the
proxy key or a token; when a probe needs it, read it from the systemd manager as in step 9.

## Rollback

| Situation | Action |
|---|---|
| A `derive --apply` made things worse | Each replaced file has a `.bak-<timestamp>` beside it in the derived root (`scripts/derive-v2-config.py:417-421`). Copy them back, then restart. Nothing was deleted. |
| A unit file was applied by a set | `python3 scripts/changeset.py revert --journal <journal-root>/opencode-v2-units/<run>/journal.jsonl --journal-root backups/changesets --allow-root ~/.config/systemd/user`, newest journal first, then `systemctl --user daemon-reload`. A hand-edited unit is reported as `drift` and left alone. |
| A plugin update broke the server | `v2-plugin-autoupdate.py` rolls itself back (exit 4) and pins the previous exact version. For a manual pin, `git revert` the pin commit (or approve a different version with `plugin_pins.py`), then `derive --apply` and restart. |
| AFT rejects every tool | Re-run `patch-aft-v2-schema.py <plugin-dir> --check`; if the cache was reinstalled, `--apply`. Restoring `.orig-0.62.0` only returns the unpatched, rejected state. |
| The whole stack | Stop V2 (`systemctl --user stop secure-opencode-v2.service opencode-perm-v2.service`), start V1 (`systemctl --user start secure-opencode.service opencode-perm.service`), then `bash verify-workflow.sh < /dev/null`. V1's files were never changed by any V2 operation. |
| Data | V1's `opencode.db` was only read by the swap and stayed the archive; after the cutover V2 writes its own copy under `~/.local/share/opencode-v2/data/opencode/`, so V1 does not see V2-era sessions. The database-level recovery commands belong to [`opencode-v2-cutover.md`](opencode-v2-cutover.md) ("Recovery"). |

Rolling back to V1 is a service switch, not a file edit, and it is temporary state: V1 resumes from
the pre-cutover history.

## V1 versus V2

| | V1 (rollback) | V2 (live) |
|---|---|---|
| Units | `secure-opencode.service`, `opencode-perm.service` | `secure-opencode-v2.service`, `opencode-perm-v2.service` |
| Config root | `~/.config/opencode` | `~/.local/share/opencode-v2/config/opencode` |
| Data root | `~/.local/share/opencode` | `~/.local/share/opencode-v2/data` |
| Port | 4096 | 4097 |
| Binary | system `opencode` | `~/.local/share/opencode-v2/prefix/node_modules/.bin/opencode2` (exact pin) |
| Deploy | verifier mirrors `global-config/` → `~/.config/opencode`, then restart | owner runs `derive --apply` → derived root, then restart |
| Verifier role | repairs the live config | reports drift, never repairs (`V2_CONFIG_ROOT_DRIFT`) |
| Config key | `plugin` | `plugins` |
| Plugin pins | exact | `~x.y.z` patch ranges |
| TUI config file | `tui.json` | `cli.json` (`tui.json` is not carried; `tui.jsonc` is never migrated) |
| Auto-update | in-process plugin | retired on V2; `scripts/v2-plugin-autoupdate.py` + timer |
| Health check on start | plugin launches the verifier | only with `WORKFLOW_HEALTH_CHECK_V2=1` |
| Permission rules | agent rule beats global | last matching rule wins (why `derive` rewrites grep and read policy) |
| Restart | `systemctl --user restart secure-opencode.service` | `systemctl --user restart secure-opencode-v2.service` |

The service units conflict (`Conflicts=secure-opencode.service` in
`changesets/opencode-v2-units/secure-opencode-v2.service`), so only one stack runs at a time.

## Common failure modes

| Symptom | Cause | Action |
|---|---|---|
| The change is not live after a restart | `derive --apply` did not run; the restart re-read the previous derivation of `global-config/` | `derive` dry run, `--apply`, restart. Never restart first and assume. |
| `V2_CONFIG_ROOT_DRIFT` in the verifier, or "file(s) differ from global-config" in the preflight | Derived root behind the source, often after a verifier commit | `derive --apply` (owner), restart |
| `refused: tools without an explicit permission rule` | A sandbox tool was added without a rule in `global-config/opencode.json` | Add the rule in the source; re-derive |
| `refused: plugin entry needs a decision` | A new `plugin` entry is not an exact pin, the fork or a known drop | Pin it exactly in the source |
| `refused: ... is inside the V1 tree` | `--target` points at `~/.config/opencode` or `~/.opencode` | Use the V2 derived root |
| 20-40 `Skipping invalid` registrations after a version bump or cache reinstall | AFT backport missing | Re-run `patch-aft-v2-schema.py --apply`, restart |
| The health check refuses to run its script | Digest pin stale after a verifier edit | `verifier_manifest.py update`, review, commit, `derive --apply`, restart |
| `plugin_pins.py` refuses with `stale` | The source pin already moved past the proposal's base | Re-read `report`; approve against the current pin |
| Preflight "unit files" WARN | Installed units differ from `changesets/opencode-v2-units` | Owner applies the set (`--dry-run` first), then `daemon-reload` |
| A hand-edited file in the derived root is overwritten by the next `derive` | The root is generated | Edit `global-config/` instead |

## Not covered here

broker's own deployment.
