# OpenCode V2 cutover runbook (queue Q46)

V2 runs beside V1 as a parallel stack: its own binary, port (4097), data, config root and units. V1 is never edited. Cutover and
rollback are therefore service switches, not file edits. The stack itself is specified in
`~/agent-sandbox-integration/docs/upgrades/opencode-v2.md` (V0-V7, the nine manual gates, "Cutover") and installed with its
`docs/upgrades/opencode-v2-install-checklist.md`. This runbook sequences the workflow-repo side and says what is automated.

**Status 2026-10-30:** V2 2.2.0 is running and passes the stack check, gate 6 (native review) has passed and the verifier has a V2 mode (Q44, reviewed); the cutover itself has not been done. The owner's target is now 2.2.3 or later (see `HANDOFF.md`). Open decisions and
engineering items are in `HANDOFF.md` ("What still stands between us and cutover").

## What is automated and what is not

| Piece | Tool | Writes? |
|---|---|---|
| Readiness report | `python3 scripts/opencode-v2-preflight.py [--stack] [--json]` | no |
| V2 config root (`~/.local/share/opencode-v2/config/opencode`, plus the Systematic server home) | `python3 scripts/derive-v2-config.py ...` | only with `--apply`; backs up differing files, never deletes, refuses V1 roots |
| The three systemd unit files | `changesets/opencode-v2-units` through `scripts/changeset.py` | only with `apply`; journal + drift-preserving revert |
| V1 config | nothing: V2 never rewrites `opencode.json` | n/a |
| Restarts, S17 installs, OpenChamber, retiring V1 | the owner | n/a |

The change set is deliberately small. Per the v4 runbook's rule ("do not invent a set"), only content that is outside git, not
regenerated, and a single file qualifies: the units. The V2 config root is regenerated by `derive`, so it is not a set.

## Steps

1. **Preflight.** `python3 scripts/opencode-v2-preflight.py --stack`. It must show no FAIL. Read every WARN. Then clear the open
   decisions in `HANDOFF.md` section B (the 2.2.3+ move and its AFT trial; V1 history; dropped config keys).
2. **Back up.** All of these, before anything else changes:
   - V1 data: `cp -a ~/.local/share/opencode ~/.local/share/opencode.bak-$(date +%Y%m%d)`
   - V2 data: `cp -a ~/.local/share/opencode-v2/data/opencode/opencode.db ~/.local/share/opencode-v2/data/opencode/opencode.db.bak-$(date +%Y%m%d)` (it holds the provider logins)
   - OpenChamber settings: `cp -a ~/.config/openchamber ~/.config/openchamber.bak-$(date +%Y%m%d)`
   - Record the OpenChamber 1.24.2 reinstall command (it is not V2-compatible).
3. **V2 beside V1.** Already installed and pinned exactly (`prefix/package.json` must read `"@opencode/cli": "2.2.0"`, no `^`
   or `~`; the preflight fails otherwise). **AFT on 2.2.5 (2026-10-31): V2 keeps AFT 0.62.0 plus a one-change backport.** AFT 0.63.4 cannot start inside the V2 sandbox (its storage lease opens `/`; `docs/upstream/aft-storage-lease-root-open.md`), but 0.62.0 registers no tools on OpenCode 2.2.1+. The fix (cortexkit/aft#1144) is plugin JavaScript only, so `scripts/patch-aft-v2-schema.py` applies it to the installed 0.62.0 plugin (`--check`, then `--apply`; it refuses any other version or build and keeps `*.orig-0.62.0`). Run it on the plugin directory the V2 config resolves to (`~/.local/share/opencode-v2/cache/opencode/npm/@cortexkit/aft-opencode@<pin>/<newest epoch>/node_modules/@cortexkit/aft-opencode`) after the 2.2.5 install and before the restart, and again after any plugin cache reinstall; the preflight's "Skipping invalid" check catches an unpatched plugin. `V2_PLUGIN_VERSIONS` in `scripts/derive-v2-config.py` stays empty until upstream fixes the lease. Trial results (2026-10-31): OpenCode 2.2.5 loads with every tool registered when AFT is patched (0 `Skipping invalid tool registration`, also inside nono with one real `read` call); unpatched 0.62.0 gives 20 in a minimal config and 40 in the full config. `derive` keeps V2 on 0.62.0 (`V2_PLUGIN_VERSIONS` empty), leaving V1's pin the same. To move the live install:
   `npm install --prefix ~/.local/share/opencode-v2/prefix --save-exact --no-audit --no-fund @opencode/cli@<version>`, restart, and
   require a clean preflight (no "Skipping invalid" tool registrations).
4. **Bring the V1 history into V2.** Stop V2, its approval watcher and V1 (`systemctl --user stop secure-opencode-v2.service opencode-perm-v2.service secure-opencode.service`), then `scripts/opencode-v2-db-swap.sh` (run it with the proxy key in its environment, in Fish `env (systemctl --user show-environment | grep '^POOL_PROXY_KEY=') bash scripts/opencode-v2-db-swap.sh`: V2 sends the credential stored for `opencode-go`, not the config's `{env:POOL_PROXY_KEY}`, and V1's own key in that row makes the proxy answer 401, so the swap sets the stored key to `POOL_PROXY_KEY` and warns when it is missing; after a proxy key rotation update that row too) (a dry run that checks everything and changes nothing) and, when it passes, `scripts/opencode-v2-db-swap.sh --apply`. V1's `opencode.db` already holds the full history in V2's tables, so V2 uses a consistent copy of it as its own database; V2's current logins are merged in and its old database files are moved to `pre-v1-history-<stamp>/` (the script prints the rollback). V1's file is only read and stays as the archive.
4b. **Apply the config.**
   - `python3 scripts/derive-v2-config.py --source global-config --sandbox-repo ~/agent-sandbox-integration --target ~/.local/share/opencode-v2/config/opencode` (dry run), then add `--apply`.
   - Units: `python3 scripts/changeset.py apply --set changesets/opencode-v2-units --journal-root backups/changesets --allow-root ~/.config/systemd/user --dry-run`, then without `--dry-run`. The drop-in directory `secure-opencode-v2.service.d` must exist first (`file_create` never creates directories). On a machine where the units are already installed, every op is `already_applied` and nothing is written.
   - `systemctl --user daemon-reload` if a unit changed.
5. **Start or restart V2 (owner).** `systemctl --user restart secure-opencode-v2.service`. V1 and V2 conflict, so V1 must be stopped first for a real cutover. Install `cli.json` before the first V2 TUI start (derive mirrors it); the `tui.json` to `cli.json` migration has not yet been observed.
6. **Verify.** (With V2 first on PATH, `bash verify-workflow.sh < /dev/null` is the V2-mode verifier: config root parity, packages, sandbox plugins, GitHub MCP, runtime agents. `--behavioral` adds the paid probes and is the one outstanding proof for section 10.) `python3 scripts/opencode-v2-preflight.py --stack` (config in sync, units match, no rejected registrations, stack check). The V2 mode of `verify-workflow.sh` (Q44) is complete except one proof: section 10's tool-event parsers have not seen a real V2 `run --format json` stream (they fail with `ODD_V2_STREAM_UNRECOGNISED` instead of passing blind), so run `--behavioral` once on V2 before treating a verifier run as the V2 acceptance gate.
7. **Manual gates (owner, with the broker).** The preflight lists them as MANUAL and never marks them passed: host read routing and mutation blocking; lazy worker activation; `sandbox_edit` mode preserved; `sandbox_apply` approval with the full preview; a `host_git_commit` approval; native review end to end; Code Mode cannot bypass approval (re-test after the `codemode: false` change); no `~/.claude` content visible; the approval prompt actually shows in the TUI.
8. **OpenChamber.** Upgrade to a V2-compatible version and point it at port 4097. Only then retire the V1 launcher. Keep the V1 tree for rollback.

## Recovery

| Symptom | Action |
|---|---|
| V2 misbehaves after the cutover | Stop V2 (`systemctl --user stop secure-opencode-v2.service opencode-perm-v2.service`), start V1 (`systemctl --user start secure-opencode.service opencode-perm.service`), run `bash verify-workflow.sh < /dev/null`. V1 files were never changed. |
| A derive `--apply` made things worse | Each replaced file has a `.bak-<timestamp>` next to it in the V2 root; copy it back. Nothing was deleted. |
| A unit file was changed by a set | `python3 scripts/changeset.py revert --journal <journal-root>/opencode-v2-units/<run>/journal.jsonl --journal-root backups/changesets --allow-root ~/.config/systemd/user`. Revert the newest journal first. A hand-edited unit is reported as `drift` and left alone. A run where every op was `already_applied` wrote nothing and has nothing to revert. |
| The V2 database will not open after a version change | Stop the service, copy the dated backup of `opencode.db` back, reinstall the previous version exactly. The 2.2.2 to 2.2.0 downgrade left `opencode.db.pre-2.2.0-downgrade` for this. |
| `opencode-perm` V2 mode misbehaves | Stop `opencode-perm-v2.service`. V1 mode is unchanged; the pre-change script is `~/.local/bin/opencode-perm.bak-20261030T115035`. |
| Tool registrations rejected again after a version bump | Pin back to the last exact version that passed. |

## Not covered here

Pushing, PRs and merges of the three branches; enabling the guarded plugin auto-update timer (`scripts/v2-plugin-autoupdate.py`);
the OpenAI login for any new V2 consumer; anything that needs the owner's secrets.
